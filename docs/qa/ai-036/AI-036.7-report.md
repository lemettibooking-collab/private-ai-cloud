## 2. Destroy / reuse decision table

Reuse happens only when every statement succeeded, or when a failure was followed by a successful ROLLBACK and the adapter did not mark the session broken.

| Situation | Caller rule | Adapter rule | Result |
|---|---|---|---|
| Every statement succeeded | reuse | not broken | **reuse** (listeners removed) |
| Server SQL error (DatabaseError, not 57P/08) inside a transaction + ROLLBACK succeeds | reuse | not broken | **reuse** |
| Server SQL error + ROLLBACK fails (any error) | destroy | — | **destroy** |
| BEGIN fails | destroy | — | **destroy** |
| COMMIT attempted and rejected (ambiguous) | destroy (+ `WorkflowRuntimeCommitAmbiguousError`) | — | **destroy** |
| Snapshot read: data error + ROLLBACK succeeds | reuse | — | **reuse** |
| Snapshot read: BEGIN, COMMIT or ROLLBACK fails | destroy | — | **destroy** |
| Single-statement read (autocommit) fails | destroy | — | **destroy** |
| Non-DatabaseError rejection (socket `ECONNRESET`, "Query read timeout", "Connection terminated unexpectedly", queue rejection, injected driver error) | — | broken | **destroy**; later queries fail fast with `PostgreSQL query failed.` without touching the socket |
| DatabaseError with SQLSTATE `57P*` or `08*`, or a malformed code | — | broken | **destroy** |
| `'error'` or `'end'` emitted while checked out | — | broken, never rethrown | **destroy** |
| Second or third `release()` call | — | no-op | pool sees exactly one release |

On destroy, the listeners stay attached, so teardown `'error'`/`'end'` events are absorbed. The pool also has its own `'error'` listener for idle clients, and it logs nothing.

## 3. Timeouts

| Setting | Value | Reasoning |
|---|---|---|
| Client `query_timeout` | **rejected** at construction (URL parsed with `URL`, case-insensitive, any position) | node-postgres abandons a timed-out statement that keeps running server-side, and silently splices out a queued ROLLBACK. That is the root of O6. |
| `idle_in_transaction_session_timeout` | **30 s** (startup option) | Runtime transactions are short statement sequences; no provider or network call happens inside a transaction. Any session idle in a transaction for 30 s is leaked, and the server ends it and releases its row locks. 30 s equals the minimum claim lease, and default and command leases are 5 min, so leaked locks clear before lease-based recovery needs them. |
| `client_connection_check_interval` | **5 s** (startup option, PostgreSQL 14+) | A backend blocked on a lock for a destroyed client notices the lost socket within 5 s. Previously it noticed only when the lock was granted. |
| `statement_timeout` | allowed in the URL; not set by default | Server-side cancel (57014) leaves the session consistent: aborted transaction, then a successful ROLLBACK, so the session can be reused. |
| URL `options`, `idle_in_transaction_session_timeout`, `client_connection_check_interval` | rejected | These are adapter-owned; the URL would override the pool config in node-postgres. |
| Non-`postgres:`/`postgresql:` or unparseable strings | rejected with `PostgreSQL configuration is invalid.` | The URL is never echoed. |

Live sessions confirmed `idle_in_transaction_session_timeout=30s` and `client_connection_check_interval=5s`.

## 7. Residual risk
- **Blast radius of destroying:** single-statement read failures now destroy the session, including validation failures in `load()` (for example an HD-4 mixed load). The cost is a reconnect, not a correctness issue.
- **PostgreSQL ≥ 14 required:** `client_connection_check_interval` is an unknown parameter on PostgreSQL 13 and older, and the connection would fail. The project targets PostgreSQL 16.
- **Connection-string format:** only URL-form `postgres:`/`postgresql:` strings are accepted. Keyword/value connection strings and URL `options` are rejected. Anyone who needs session options must add them to the adapter's constant.
- **Idle-in-transaction timeout:** a transaction that is legitimately idle for more than 30 s is terminated. No such path exists today. A future long-running transaction would need to revisit this value.
- **Not covered here:** wire-level TCP loss (still driver-boundary simulation only), and HD-1 … HD-11 (AI-037 backlog, out of scope as instructed, including HD-4).
- **Wrapper-bypass paths:** the tenant resolver and all store and read-model paths go through `createWorkflowRuntimePostgresDatabase`. A custom `WorkflowRuntimeDatabase` that bypasses the wrapper gets only the caller-level destroy rules, not the adapter-level broken tracking.
