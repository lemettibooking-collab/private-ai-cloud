## Архитектурное решение ADR-001: оркестратор и специализированные агенты

**Статус:** принято 14 августа 2026 года  
**Приоритет:** фундаментальный принцип архитектуры

**Обновление v0.2 от 14 августа 2026 года:** зафиксированы multi-provider слой OpenAI / Anthropic / DeepSeek / Qwen, роль Qwen Developer Agent и поэтапная модель допуска AI-разработчиков.

## Решение

Платформа строится не вокруг одной универсальной модели, которая напрямую выполняет все функции, а вокруг **центрального оркестратора**, управляющего набором специализированных агентов, инструментов и детерминированных рабочих процессов.

Модель является сменяемым компонентом reasoning-слоя, а не всей системой. Для разных задач оркестратор может выбирать разные модели и провайдеров по качеству, стоимости, скорости, приватности и уровню риска.

## Ответственность оркестратора

- принять задачу пользователя или системное событие;
- определить тип задачи, риск, требуемые данные и разрешения;
- составить план и выбрать подходящего агента или workflow;
- подобрать модель и инструменты;
- передавать между агентами только необходимый контекст;
- запрашивать подтверждение человека перед критическими действиями;
- контролировать лимиты времени, стоимости и числа итераций;
- проверять результат и при необходимости направлять его на review;
- сохранять журнал действий, источников, решений и ошибок;
- останавливать или изолировать небезопасное выполнение.

## Специализированные роли MVP

- **Owner Assistant** — сводка состояния продукта, очередь подтверждений и рекомендации владельцу.
- **Knowledge Agent** — поиск и подготовка ответов на основе загруженной базы знаний.
- **Support Agent** — черновики ответов для ручной вставки вопроса, Telegram-бота и чата сайта.
- **Telegram Content Agent** — подготовка контента; сначала draft-only, далее approval → publish.
- **Product Analyst Agent** — анализ поддержки, багов, feature requests, лидов и продуктовых сигналов.
- **Codex Task Agent** — формирование узкого задания, copy-ready промпта и Markdown-файла для Codex.
- **Codex Developer Agent** — основной исполнитель утверждённых задач разработки; работает только после запуска Owner, готовит минимальный patch и результаты проверок, не выполняет автоматический merge.
- **Qwen Developer Agent** — дополнительный разработчик и независимый reviewer на базе Qwen Code; внедряется поэтапно от read-only анализа до ограниченной sandbox-разработки.
- **QA/Review Agent** — анализ вручную вставленных diff и логов; позже интеграция с local runner.
- **Security/Compliance Agent** — контроль политик, разрешений, утечек данных и опасных действий.
- **Report Agent** — Weekly Owner Report и другие утверждённые отчёты.

На старте эти агенты являются **логическими ролями, инструкциями и workflow внутри общего приложения**. Они не обязаны быть отдельными сервисами или постоянно запущенными процессами.

## Модельный и агентный слой

Оркестратор и специализированные агенты принадлежат нашему приложению. Внешние модели подключаются как сменяемые вычислительные провайдеры через API и не получают право напрямую управлять платформой.

Целевые провайдеры:

- **OpenAI** — основной reasoning- и coding-провайдер первой версии; Responses API / Agents SDK применяются через серверный адаптер.
- **Anthropic** — дополнительный провайдер для сложного анализа, coding/review и независимой проверки через нативный Claude API.
- **DeepSeek** — дополнительный экономичный провайдер для массовых и agentic-задач через совместимый API-адаптер.
- **Qwen / Alibaba Model Studio** — провайдер Qwen-моделей; Qwen Code используется как изолированный coding harness для Qwen Developer Agent.

Все обращения проходят через внутренний `ModelProvider` / `ModelRouter`. Бизнес-логика и политики не должны зависеть от конкретного model ID или SDK.

Оркестратор остаётся гибридным:

- детерминированный код управляет ролями, приоритетами, очередями, approval, бюджетами, блокировками и audit;
- Manager Agent помогает классифицировать нестандартные задачи, строить планы и объединять результаты;
- модель не может отменить жёсткое правило Policy Engine.

## Протоколы интеграции

- **Provider API** используется для вызова OpenAI, Anthropic, DeepSeek и Qwen.
- **Внутренние функции и очередь задач** используются между логическими агентами MVP.
- **MCP** добавляется для стандартизированного подключения повторно используемых инструментов и данных.
- **A2A** не требуется для вызова модели; он применяется позднее только для связи с независимыми удалёнными agentic-сервисами.

Специализированные агенты не общаются друг с другом произвольно: передача задач, контекста и результатов проходит через оркестратор и фиксируется в Audit Log.

## Политика Qwen Developer Agent

Qwen включается в проект как дополнительный разработчик, а не как единственный автономный исполнитель.

Этапы допуска:

1. **Researcher:** read-only анализ репозитория, root cause, карта файлов и план исправления.
2. **Reviewer:** независимая проверка diff Codex, поиск регрессий и пропущенных тестов.
3. **Test Engineer:** создание и запуск тестов в sandbox без изменения production-контуров.
4. **Developer:** небольшие изменения в отдельной временной ветке/worktree и контейнере.
5. **Long-running Developer:** длительные ограниченные задачи только после прохождения evals и quality gates.

Обязательные ограничения Qwen:

- отдельная ветка или git worktree;
- Docker/Podman sandbox;
- лимит времени, токенов, стоимости и числа итераций;
- allowlist команд и инструментов;
- отсутствие production-секретов и прямого доступа к production-БД;
- запрет на `main`, merge, push в защищённую ветку и deploy;
- запрет на live trading, реальные ордера и финансовые операции;
- режимы Plan / Ask Permissions / Auto-Edit / ограниченный Auto; YOLO запрещён для рабочих репозиториев;
- обязательный diff, логи проверок и итоговый handoff;
- независимый QA/Security review до принятия результата.

Codex и Qwen не должны одновременно изменять одни и те же файлы. Оркестратор либо разделяет области владения, либо использует одну модель как исполнителя, а вторую как reviewer.

## Базовый поток

1. Пользователь, API, Telegram или внутреннее событие создаёт задачу.
2. Оркестратор классифицирует её и назначает уровень риска.
3. Policy Engine проверяет роль пользователя, разрешения и допустимые инструменты.
4. Оркестратор выбирает агента, модель, контекст и workflow.
5. Агент готовит результат или предложение действия.
6. Критическое действие попадает в Approval Queue.
7. После подтверждения исполнитель выполняет действие.
8. QA/Review проверяет результат, а Audit Log сохраняет полный след выполнения.

## Обязательные архитектурные свойства

- **Model/provider agnostic:** возможность менять модели без переписывания бизнес-логики.
- **Multi-model routing:** сильная reasoning-модель для сложных решений, дешёвая быстрая модель для массовых операций, локальная модель для чувствительных данных при необходимости.
- **Human-in-the-loop:** финансовые, публикационные, внешние и необратимые действия требуют подтверждения согласно политике риска.
- **Least privilege:** каждый агент получает только минимально необходимые инструменты и данные.
- **Изолированное выполнение:** код и опасные инструменты запускаются в ограниченном окружении.
- **Наблюдаемость:** трассировка задач, стоимость, задержка, ошибки, версии промптов и моделей.
- **Надёжные workflow:** критические этапы задаются детерминированной логикой, а модель используется там, где действительно требуется рассуждение.
- **Fallback:** при ошибке модели или провайдера задача безопасно останавливается либо переводится на разрешённый резервный маршрут.
- **Контроль контекста:** персональные и закрытые данные не передаются агентам и провайдерам без необходимости и разрешения.

## Интерфейс продукта

Решение сохраняет принятый UX-контур:

- основной экран Owner: **Approval Queue + Activity Summary**;
- основные разделы: **Dashboard, Workflows, Approvals**;
- пользователь работает с понятными формами и результатами, а не вручную запускает пять агентов;
- позднее может быть добавлен единый ассистент-чат, через который оркестратор управляет workflow.

## Границы MVP

В первый MVP не входят:

- полностью автономные действия без политик и подтверждений;
- отдельный микросервис для каждого агента;
- свободное общение агентов без лимитов и журналирования;
- автоматический merge кода;
- автоматический deploy кода, созданного AI-разработчиком;
- запуск Codex кем-либо, кроме Owner;
- автономная работа Qwen вне sandbox или с production-доступом;
- YOLO-режим coding-агента в рабочих репозиториях;
- публикация или отправка внешних сообщений без предусмотренного approval;
- привязка всей системы к единственной модели или поставщику.

## Эволюция после MVP

1. Добавить единый реестр агентов, инструментов и разрешений.
2. Реализовать OpenAI provider adapter как первый рабочий модельный маршрут.
3. Ввести `ModelProvider` / `ModelRouter`, затем добавить Anthropic, DeepSeek и Qwen через отдельные адаптеры.
4. Запустить Qwen Researcher и Qwen Reviewer на эталонном наборе задач Smart Algorithms.
5. Добавить изолированный Qwen Code worker для Test Engineer и небольших patch-задач.
6. Поддержать MCP для подключения инструментов и данных.
7. Поддержать A2A только для независимых удалённых agentic-сервисов.
8. Вынести ресурсоёмкие или высокорисковые роли в изолированные workers/сервисы.
9. Добавить автоматические evals, replay задач, бюджеты и quality gates.
10. Развивать автономность только после подтверждения её надёжности на реальных сценариях.

## Критерий принятия следующих решений

Любая новая функция должна отвечать на вопросы:

1. Это ответственность оркестратора, специализированного агента, инструмента или детерминированного workflow?
2. Какой агент имеет право её выполнять?
3. Какие данные и разрешения ему действительно нужны?
4. Требуется ли подтверждение человека?
5. Как действие журналируется, проверяется и безопасно останавливается?
6. Можно ли заменить модель или провайдера без изменения продуктовой логики?
